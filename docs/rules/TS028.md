# TS028 no-silent-error-swallow

The severity is error; the rule is on by default and stable.

## Reports

An error is handled, propagated, or crashed on by name, never dropped.

Reporting unit: Each site.

Anchor: The discarding expression.

Carve-outs: A file-local function is fallible when its return type carries the language's error
marker (`Result<`, `error`, `!`, `?`, `Maybe(`), spells `Error` or `Errno` in any case, or ends
in a `bool` after another result, which is Odin's and Go's comma-ok shape. Each language
reports a bare statement, including one under `defer`, `errdefer`, or `go`, that calls a
fallible file-local function and drops its result, and a declaration or assignment whose last
bound name is the discard (`_ = load()`, `let _x = load()`, `x, _ := pair()`, `_, _ = pair()`)
when the call is fallible; the last name is the one judged because Go and Odin return the error
last, so `_, err := os.Open(path)` binds the error and stays quiet.

Rust reports `.ok()`, `.err()`, and `.ok_or_default()` on a discarded result, the same chain under a
`let _` binding, `unwrap_or`, `unwrap_or_default`, `unwrap_or_else`, `ok_or`, and `ok_or_else` on a
fallible file-local receiver in any position, because the default hides the failure, except where a
`?` sits between the call and the default, `load()?.unwrap_or(0)`, since the error has already been
propagated and the default fills an absence. An `ok_or` or `ok_or_else` turns an absence into an
error, so it reports only where its receiver discards one, `load().ok().ok_or(fallback)`; on any
other receiver it supplies no default and hides nothing, as `Self::field_at(self,
index).ok_or_else(...)` shows wherever the name resolves to a function that returns an `Option`. An
`unwrap_or_else` whose closure does nothing but `panic!`, `unreachable!`, `todo!`, or
`unimplemented!`, `|err| panic!("{err}")` with or without a block and a semicolon, crashes on the
error by name as `expect` does and is quiet. Rust also reports `drop`, `forget`, `mem::drop`,
`mem::forget`, and their `std::` and `core::` spellings around a fallible call; an empty `Err(_) =>
{}` or `Err(_) => ()` arm; and an empty `if let Err(_) = load() {}` body. A wildcard or a binding,
`Err(_)` or `Err(error)`, catches each error, while a pattern that names its variant through a path,
`Err(ValError::Omit) => ()` or `if let Err(TryRecvError::Empty) = held {}`, handles that one error
by name, as TigerBeetle's own `error.WouldBlock => {}` prong does, and is quiet. `unwrap` and
`expect` stay quiet, since they crash by name. The `.ok()` and `.err()` shapes are method calls read
by the method's own name, so `held.ok();` reports whatever its receiver is called and
`err.valid_up_to()` calls `valid_up_to` rather than `err`; a free function that shares the name,
`ok("unix");` under a file-local `fn ok(s: &str)`, has no receiver, discards no result, and is
quiet.

Zig reports a `catch` whose handler block is empty, whether the capture is absent, `|_|`, or
`|err|`, and a handler whose only statement is `_ = err` for its own capture; an `else |_| {}`
on an `if` over an error union; and the same shapes inside `defer` and `errdefer`, since an
error dropped in a defer is still dropped and a log or a panic is the handling. The bare-call
shape is not reported in Zig, because the compiler rejects a discarded error union
(`error: error union is ignored`), which `compiler_rejects_a_dropped_error` records.
A Rust macro invocation is no call of the function its name shares: `try_recv!();`, expanding a
`macro_rules! try_recv` the function declares, is quiet beside a fallible `fn try_recv`, since
macros and functions live in separate namespaces.
A Rust call with no receiver and no path, `write_help(&mut styled, self, &usage, false);`, cannot
reach a method that takes `self`, so a file-local method of that name does not make it fallible.
A Rust call through a module path, `accel::find_fwd(needles, haystack, at)` or `super::load()`,
names another module's function, so a file-local function of the same name does not make it
fallible either; `self::find_fwd(...)` and a call into a `mod` the file declares still reach it.
A call inside a function that declares a nested function of the callee's name reaches that nested
function, which shadows the file's namesake, so `parse(1, true);` under a nested `fn parse(size:
usize, ok: bool) { ... }` drops nothing even where a top-level `parse` returns a `Result`.

Go's `Close`, `Commit`, `Flush`, `Rollback`, and `Sync` list applies to a method on a value,
never to a package function such as `xhttp.Flush(w)`, which is told apart because the receiver
names an import.

Go and Odin report an empty branch on `name != nil` or `name != .None`, including the
init-statement form `if err := load(); err != nil {}`, where the name is `err`, is bound in the
branch's own header, is the last name of a multi-name binding, or is bound from a fallible
file-local call; and Go reports a bare `Close`, `Commit`, `Flush`, `Rollback`, or `Sync` method
call whose result is dropped, `defer f.Close()` included, because P10 names `close` as the call
whose result must be checked or voided explicitly. Odin reports `call() or_else 0` and
`call() or_else {}` on a fallible file-local call, since a literal fallback hides the error.

JavaScript and TypeScript report an empty `catch (error) {}` block and an empty function
literal handed to `.catch(...)` or as the second argument of `.then(...)`.

A `catch` whose decision is written down is handled rather than dropped. The swallow is exempt
when the comment block directly above the line its statement starts on, each comment on a line
of its own and no blank line between, names the error or says it is ignored: some comment in the
block holds `error`, `ignore`, or `ignoring` in any case, so `Errors` and `ignored` count. A
block opening `// The error from .open_sync() is ignored` above
`multiversion_os.?.open_sync() catch {};` exempts it, and the same block above a `defer` or
`errdefer` that swallows does too. A block that also holds a `FIXME` or an uppercase to-do
marker defers the handling rather than deciding it, and reports. A comment below the statement,
one past a blank line, one trailing the swallow's line or another statement's, a `tigerstyle-`
directive, and a comment that speaks only of the call, `// Flush before returning.` above
`flush() catch {};`, explain nothing, and the swallow reports. The block is read above the line
the swallowing expression starts on, so an `else |_| {}` and a `} catch (error) {}` clause, whose
line opens with the brace that closes the guarded block, report whatever their comments say, as
do the other shapes above.

## Does not report

The rule reaches Go, JavaScript, Odin, Rust, TypeScript, and Zig. Python signals failure
by raising, which TS009 and TS010 already cover.

A finding is suppressed by a `tigerstyle-ignore:` directive naming TS028, by a
`tigerstyle-file-ignore:` directive, or by a `tigerstyle-disable:` region covering the line.

## Known false positives

The shapes that misfire here are `swallowed-catch` and `cross-file-fallibility`.

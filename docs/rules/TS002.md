# TS002 function-too-long

The severity is warning; the rule is on by default and stable.

## Reports

A function fits in 70 lines, so one screen holds the whole unit of work.

Reporting unit: Each function, where a function is a declaration or a lambda bound to a name: a
JavaScript or TypeScript arrow or function expression assigned to a `const`, `let`, or
property, a Go `var f = func() {}` or `f := func() {}`, a Rust closure bound with `let`, a
Python `f = lambda`, and an Odin `f := proc() {}`. A lambda passed straight to a call is
TS015's and is not measured here.

Anchor: The first token of the line the function header opens on, which for a bound lambda
is the line that binds the name.

Carve-outs: Zig exempts a function whose spelled return type is exactly `type`, since such a
function is a namespace rather than a unit of work, and the language has no other way to
declare a generic type. Python measures to the last non-blank line of the block, because the
dedent that ends a Python block is recorded at the start of the next line and would otherwise
add the blank lines below the function to its span.

## Does not report

The rule reaches every language tigerstyle-lsp lints.

A finding is suppressed by a `tigerstyle-ignore:` directive naming TS002, by a
`tigerstyle-file-ignore:` directive, or by a `tigerstyle-disable:` region covering the line.

## Known false positives

There are none recorded.

## Citations

TigerStyle: "There's a sharp discontinuity between a function fitting on a screen, and
having to scroll to see how long it is. For this physical reason we enforce a hard limit
of 70 lines per function."

NASA P10 Rule 4: "No function should be longer than what can be printed on a single sheet
of paper in a standard reference format with one line per statement and one line per
declaration. Typically, this means no more than about 60 lines of code per function."

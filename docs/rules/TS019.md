# TS019 restrict-pointers

The severity is error; the rule is opt-in by default and stable.

## Reports

A raw pointer takes the lifetime out of the type, so nothing checks the access that follows.

Reporting unit: Each type occurrence, plus one per unsafe block and one per unsafe declaration in
Rust.

Anchor: The type node, or the node the `unsafe` keyword opens.

Carve-outs: The classification is per language, over the text of a `Type` node and over the rest of
the line at each token. Rust reports `*const` and `*mut` types, and reports `unsafe` on a
function, `impl`, `trait`, or `extern` block under a second message; an `unsafe` block is the
confinement the message asks for and is not reported. Go is silent on a plain `*T` and reports
the six `unsafe.*` names (`Add`, `Pointer`, `Slice`, `SliceData`, `String`, `StringData`) and
`uintptr`. Zig reports a `[*` many-pointer and a pointer to `anyopaque`, and is silent on `*T`
and `*const T`. Odin reports `rawptr`, `uintptr`, a `[^]T` multi-pointer, and a `transmute(^T)`
that manufactures a pointer from an integer, and is silent on `^T`. Python reports the `ctypes`
pointer surface: `ctypes.pointer`, `ctypes.POINTER`, `ctypes.cast`, `ctypes.c_void_p`, and the
bare `POINTER` and `c_void_p` an import brings in; `ctypes` is an FFI boundary, and the rule
reports the pointer at the place the program manufactures it. The name a `def` or `class` declares
is a definition rather than a use, so `def POINTER(cls: type[_CT]) -> type[_Pointer[_CT]]: ...` and
`class c_void_p(_SimpleCData[int | None]):` in a stub are quiet, while a `c_void_p` in the
signature's return type still reports.

A signature is not exempt by being a signature. A pointer in a parameter list, a return type, a
local, a field, or a type alias reports alike, since the rule forbids the pointer type wherever it
is written, and `type P = *const u8` reports whatever the enclosing function returns. The exemption
is a foreign boundary, where the other side dictates the type: a line that carries a boundary
marker, each line inside a block that opens with one, and each line of a function signature that
carries one on any of its lines, so a C ABI signature wrapped over several lines, with
`callconv(.c)` on its closing line, is quiet as its one-line form is. The markers are Rust `extern`,
Zig `callconv`, `export`, `extern`, and `opaque`, Odin `foreign`, and Go `Call` and `Syscall`, which
also covers each argument line of a multi-line `.Call(` invocation. Python has no marker, so a
`ctypes` pointer reports everywhere.

A function the file hands over as a value has its signature dictated the same way, by the function
type it fills. The file hands a function over when it names the function without calling it, as
`.alloc = alloc` does in a `std.mem.Allocator` vtable, so the `?[*]u8` that `alloc` and `remap`
return is quiet. A function written in place as a call argument, a field value, or the value of a
member assignment is handed over where it is written, as Rust's `.map(|p: *const u8| ...)` is, and
so is a function an anonymous container declares when the file names it through that container,
`struct { fn ready(ptr: *anyopaque) void {} }.ready`, or through parentheses that wrap exactly that
container, `(struct { ... }).ready`, the spelling a field value or an argument usually takes. The
position is read where the container expression starts, so `const ready = (struct { ... }).ready;`
is an untyped alias and hands nothing over. A pointer in the body of such a function still reports.
A Rust function written directly as the input of a macro invocation, `ffi_fn! { fn
rure_free(re: *const Regex) { ... } }`, is handed to that macro and carries the signature the
macro gives it, such as the `#[no_mangle] pub extern fn` that `ffi_fn!` emits, so the pointers
on its signature lines are quiet while a pointer in its body still reports. A configuration
macro, one whose name begins with `cfg`, gates its input and emits it unchanged, so a function
inside `cfg_io! { ... }` keeps its own signature and reports.
An untyped alias such as `pub const build = run;`, a comparison, an export, and an Odin procedure
group `proc{first, second}` name a function without handing it over, since none of them fixes a
signature, and a generic call such as `run::<T>(value)` is a call. A switch prong hands a function
over exactly when the switch itself would: a prong of a switch that is a field value, an argument,
or a return value, `.stepFn = switch (mode) { .simd => stepSimd }`, fills the field's function type
as `.setupFn = setup` does, while a prong of a switch bound to an untyped alias, `const step =
switch (mode) { ... }`, does not. An Odin procedure whose body is `---` declares a signature that a
foreign library or the compiler defines, so the `uintptr` of a builtin's declaration is quiet.

A function pointer is exempt, in a single-line or a multi-line spelling, and so is each pointer
inside its parameter list: Rust `fn(*const u8)`, Go `func(unsafe.Pointer)`, Zig `*const fn
(*anyopaque) void`, and Odin `proc(rawptr)`, with or without the calling convention Odin may spell
between the word and the list, `proc "system" (this: ^IUnknown, out: ^rawptr)`. NASA P10 Rule 9
forbids function pointers outright; TigerStyle uses callbacks throughout, names them
(`read_sector_callback`), and orders parameters around them ("Callbacks go last"), so the rule
follows TigerStyle here and leaves the callback alone. This is a deliberate choice of TigerStyle
over P10, and the Rule static cites both.

The context a callback receives is exempt with the callback: a name that is, or ends in `_` and
then, `context`, `ctx`, `user_data`, or `userdata` carries no finding whatever pointer it is
typed. The reason is the paragraph above. A rule that permits `*const fn (*anyopaque) void` and
then reports the `*anyopaque` the callback is handed forbids half of an idiom it has already
allowed, and the erased context is the half the callee cannot choose. The name is read back
through the type's own punctuation, so `user_data: ?*anyopaque`, `ctx unsafe.Pointer`, and
`ctx: *mut c_void` are all exempt.
A pointer under any other name reports, `buffer: *anyopaque` included, except a parameter the
language discards: `_: ?*anyopaque` reads nothing through its pointer and exists only because the
function type it fills declares it, as TigerBeetle's `fn realtime(_: *anyopaque) i64` does.

A multi-level dereference, `**T` or `^^T`, is TS051's finding, not this rule's, and so is a raw pointer to
a raw pointer: neither level of `*const *const str` or `*mut *mut u8` reports here.

## Does not report

The rule reaches Go, Odin, Python, Rust, and Zig. JavaScript and TypeScript have no pointer type;
each name binds a reference the runtime owns.

A finding is suppressed by a `tigerstyle-ignore:` directive naming TS019, by a
`tigerstyle-file-ignore:` directive, or by a `tigerstyle-disable:` region covering the line.

## Known false positives

The shapes that misfire here are `function-literal-not-a-pointer`, `function-pointer-anchor`, `audited-unsafe-block`, `function-pointer-field`, `platform-boundary-pointer`, and `nested-literal-anchor`.

## Citations

NASA P10 Rule 9: "The use of pointers should be restricted. Specifically, no more than one
level of dereferencing is allowed. Pointer dereference operations may not be hidden in
macro definitions or inside typedef declarations. Function pointers are not permitted."

TigerStyle: "Callbacks go last in the list of parameters. This mirrors control flow: callbacks
are also _invoked_ last."

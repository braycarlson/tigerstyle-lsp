# TS047 assert-implication

The severity is info; the rule is opt-in by default and stable.

## Reports

An `if` whose whole body is one assertion states an implication, so it is written on one line.

Reporting unit: Each branch.

Anchor: The branch.

Carve-outs: A branch carrying an `else` arm is exempt, since it is a case split rather than an
implication. A branch already written on one line is exempt. The body must hold exactly one
statement, counted as statements rather than as newline tokens, and that statement must be an
assertion. A braceless body counts: `if (a)` with `assert(b);` on the next line reports. A
braceless body that follows an `else` is that arm of a case split, so an `if` expression
such as `if (ready) remove(key) else unreachable` is quiet however its lines fall. The
statement is an assertion when TS004 names it one in itself, and Odin's `panic(` is not
one: `if !ok { panic("...") }` is the whole assertion idiom rather than an implication
that guards an assertion.

A branch whose condition spans more than one line is exempt. The condition alone does not
fit on one line, so the implication cannot either, and the wrapped form is the one
TigerBeetle writes: `if ((key_size == 8 and value_size == 128) or` over three more lines of
its condition, then a braced `assert(data.padding_size == 0);`.

A branch reports only when its single-line form fits within `line_length_max` columns, 100
by default, counted as TS012 counts them. TigerStyle limits a line to 100 columns "without
exception", so an implication too wide to fold keeps its braces, as 38 of TigerBeetle's do:
`if (header.op <= self.op_prepare_max())` with its assertion would fold to 123 columns and
is quiet. The width is the branch's own line up to its condition, one space, and the
assertion's line from its first character. Odin's one-line branch spells `do` before its
statement, so its width counts `do` and one more space: `when
intrinsics.has_target_feature("atomics")` with `assert(intrinsics.atomic_load(&a.mu) !=
.Unlocked)` folds to 103 columns behind its tab and is quiet. A language whose formatter splits a
one-line branch is measured by the formatter's form instead, so the limit does not apply there.

The one statement must be the assertion itself. A nested `if`, a loop, or a `switch` whose own
body asserts is control flow around the assertion, so `if (a) { if (b) assert(c); }` and `if
(a) { for (items) |item| assert(item > 0); }` are quiet: the outer branch does not fold onto the
inner one's line, and the nested form is the split condition the standard asks for.

The assertion must sit on one line; a multi-line assertion is exempt, since it would not fold
into the `if`.

Where the language's formatter splits a one-line branch, the split form is the one-liner:
gofmt and rustfmt expand `if a { assert(b) }` to three lines, and black expands `if a:
assert b` to two. The branch in Go, Rust, and Python is therefore exempt at that height,
and reports only when it spans more lines than the formatter's own form needs, such as a
comment or a blank line beside the assertion. A Rust `if let` binds a pattern and is not
an implication.

## Does not report

The rule reaches every language tigerstyle-lsp lints.

A finding is suppressed by a `tigerstyle-ignore:` directive naming TS047, by a
`tigerstyle-file-ignore:` directive, or by a `tigerstyle-disable:` region covering the line.

## Known false positives

The shape that misfires here is `assertion-through-try`.

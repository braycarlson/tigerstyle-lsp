# TS004 assert-density

The severity is info; the rule is opt-in by default and stable.

## Reports

A file carries at least two assertions per function on average, covering preconditions and
postconditions.

Reporting unit: Each file. A single finding names the whole shortfall rather than one finding
per function.

Anchor: The first position in the file, a zero-width span at offset zero.

Carve-outs: Each function whose body holds at least one statement joins the denominator; the
standard sets no size floor, so a one-line helper counts like any other, and a test function counts
like any other. A function with an empty body stays out, since there is nothing in it to check. A
Rust `fmt` method inside an `impl ... for ...` block, whose header may wrap its `for` onto a later
line, stays out too: its signature is `core::fmt`'s, its parameters carry no precondition the trait
lets the author state, and its body renders state that the type's constructors already checked. A
statement is a declaration, an assignment, a branch, a loop, a match, a return, a try, an except, or
an expression statement; a Python `with` statement is one too, so a function whose body is one
`with` block joins the denominator; an item the body declares, a nested function, struct, `impl`, or
class, is a declaration too; and a macro invocation counts twice where the language spells one with
a bang, which keeps a Rust `println!` alone in a body a function with a body.

An assertion is a token the language spells as one, counted over each function in the file: Go
`assert(` and the `require.X(` and `assert.X(` families; JavaScript `assert(`, `assert.ok(`,
`assert.strictEqual(` and the rest of the node `assert` module, `expect(`, and `invariant(`; Python
`assert`, `assert_*(`, and unittest's `self.fail(` and the `self.assert` and `self.fail` helpers
whose next letter is a capital, `self.assertEqual(` and `self.failUnless(`, so `self.fail_login()`
and `self.failureException(...)` are no assertion, and a `self.fail(` in a file that declares its
own `def fail(` calls that method, an error reporter such as mypy's `TypeChecker.fail`, rather than
unittest's; Rust `assert!`, `debug_assert!`, `prop_assert!`, their `_eq`, `_ne`, and `_matches`
forms, and `unreachable!`; Zig `assert`, `unreachable`, and the `std.testing.expect*` family,
through its full path or through a call of a file alias such as `const expect =
std.testing.expect;`; and Odin `assert(` and `ensure(`. Odin `panic(` and `unimplemented(` are not
assertions in themselves: a stub is not a check.

A `panic(` call whose enclosing statement is an `if` with no `else` counts as one assertion,
because that is the assertion idiom in a language without an assert statement: Go `if x < 0
{ panic("negative") }`, Odin `if x < 0 { panic("negative") }`, Rust `if x < 0 { panic!() }`,
and Zig `if (x < 0) @panic("negative")`. A `panic` on one arm of an `if`/`else` is a
control-flow choice and does not count.

An assertion a static check can prove never fails does not count, as NASA P10 Rule 5 says:
one whose condition is a literal `true`, `True`, or `1`, and one that compares a term with
itself, such as `assert(a == a)`. A comparison form, `assert_eq!(1, padding_len(11))` or
`expectEqual(true, done())`, holds two values rather than one condition, so a literal first
value leaves it counted. A definition whose name opens like an assertion, such as
Python's `def assert_valid(x):`, is not an assertion either; the name that follows `def`
or `function` is excluded.

## Does not report

The rule reaches every language tigerstyle-lsp lints.

A finding is suppressed by a `tigerstyle-ignore:` directive naming TS004, by a
`tigerstyle-file-ignore:` directive, or by a `tigerstyle-disable:` region covering the line.

## Known false positives

The shapes that misfire here are `density-count` and `dot-directory-walked`.

## Citations

TigerStyle: "The assertion density of the code must average a minimum of two assertions
per function."

NASA P10 Rule 5: "The assertion density of the code should average to a minimum of two
assertions per function. [...] Any assertion for which a static checking tool can prove
that it can never fail or never hold violates this rule. (I.e., it is not possible to
satisfy the rule by adding unhelpful "assert(true)" statements.)"
